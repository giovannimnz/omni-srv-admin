# G18 Ubuntu Pro/ESM Upgrade Gates

Canonical Phase 28 -> Phase 29 gate for the G18 Ubuntu Pro/ESM upgrade.

This runbook satisfies G18-02 for the preparation phase: it turns the
read-only inventory into a concrete PASS/BLOCK gate before any package
mutation. It does not authorize or execute live upgrade work by itself.

## Hard Boundary

No Phase 28 live mutation was executed or is authorized by this document.

Forbidden in Phase 28:

- `apt update`, `apt upgrade`, `apt full-upgrade`, `apt autoremove`, package install/remove.
- XRDP/RDP restart or session cleanup.
- PM2 restart, `pm2 save`, `pm2 resurrect`, or process repair.
- Landscape registration mutation or self-hosted Landscape deployment.
- Webhook POST.

Phase 29-only concerns:

- Live apt mutation.
- Post-mutation Microsoft RDP validation.
- Landscape SaaS UI online confirmation.
- Any PM2/XRDP restart or repair action.

## Gate Semantics

| Status | Meaning |
| --- | --- |
| PASS | The required evidence exists and is fresh enough for the Phase 29 approval window. |
| REVIEW | The evidence exists, but the operator must explicitly accept the posture. |
| BLOCK | Phase 29 package mutation must not start until the listed artifact is produced or an operator-signed exception is attached. |

Fresh inventory rule: the approval record must reference an inventory report
captured within 2 hours of the intended Phase 29 mutation start. The current
Phase 28 inventory is a planning baseline; if it is older than 2 hours at the
Phase 29 window, regenerate it before approval.

## Required Phase 29 Preflight Bundle

Create one dated bundle per host before any package mutation. The bundle path
must be written in the operator approval record.

Required files per host:

- `inventory-report.md`: fresh redacted inventory generated by `scripts/g18-pro-esm-inventory.py`.
- `dpkg-selections.txt`: output from `dpkg --get-selections`.
- `pro-status.json` or `pro-status.txt`: Ubuntu Pro status capture with account/contract/token values redacted in any shared artifact.
- `upgradable.txt`: `apt list --upgradable` capture from the current apt cache unless Phase 29 explicitly approves `apt update` first.
- `kernel.txt`: `uname -r` capture.
- `pro-collect-logs.tar.*`: `pro collect-logs` output stored on the host or secured backup path, not pasted into docs.
- `apt-sources-manifest.txt`: source file metadata and review notes; source contents are not copied into planning docs.
- `service-baseline.txt`: read-only state for `landscape-client`, `xrdp`, `xrdp-sesman`, `pm2-ubuntu`, and `k3s`.
- `checkpoint.md`: written operator checkpoint with host, package scope, snapshot ID or exception, backup path, expected reboot posture, expected service-restart posture, signed timestamp.

Do not paste Ubuntu Pro tokens, account IDs, contract IDs, API keys,
Cloudflare tokens, Landscape credentials, or webhook secrets into the bundle
or any planning artifact.

Phase 29 must not run package mutation without one approval record per host.
The record may be in a planning file, ticket, or signed operations note, but it
must contain all fields below.

```text

preflight_bundle_path:

landscape_saas_validation_owner:
rollback_path:

```

Minimum approval statement:

```text
I approve Phase 29 package mutation for <host> using <package_scope>.
I have reviewed the inventory, snapshot/exception, backup path, rollback path,
and expected no-reboot/no-service-restart posture.
```

## Rollback Protocol

Rollback is decided per host. Do not improvise broad service restarts during an
incident; use the captured artifacts and the least destructive path that
matches the failure mode.

### Decision Points

| Failure mode | First rollback path | Required evidence |
| --- | --- | --- |
| Package upgrade failure but SSH works | Package-level rollback from captured versions and `dpkg --get-selections` | Preflight bundle, apt logs, package scope, exact before/after package versions. |
| Ubuntu Pro/ESM source or attach regression | Restore Pro service/source state from captured `pro status`, apt source manifest, and approved secret path if attach is needed | Redacted Pro status, token metadata path, source manifest; no token values in docs. |
| Landscape client offline after mutation | Observe local client and SaaS state, then decide re-registration in Phase 29 gate | Landscape local state, SaaS UI evidence, no self-hosted deployment. |
| RDP/XRDP login regression | Use network map and saved XRDP config/session references; avoid restart unless Phase 29 approval explicitly permits it | Config backup path, display `:1` reference, `xrdp`/`xrdp-sesman` baseline. |
| Host inaccessible or system state corrupted | OCI restore path if a real snapshot exists | Real `ocid1.image...` snapshot ID, OCI restore drill/runbook, backup path. |
| No real snapshot exists | Operator-signed exception path only | Signed exception acknowledging manual rebuild/package rollback risk. |

### OCI Restore Notes

Phase 15 left `pending-*` snapshot IDs as offline planning records because OCI
CLI/config were absent. A `pending-*` value is not a real restore point.

For Phase 29 mutation, the gate must include one of:

- A real OCI image snapshot ID beginning with `ocid1.image...`.
- A signed exception that explicitly accepts no OCI restore path for that host.

`docs/operations/oci-snapshots.md` is the source of truth for restore drill and
OCI restore decision details. Real restore work remains a gated Phase 29 or
incident-response action, not a Phase 28 action.

### Package Rollback Inputs

The rollback owner must have:

- `dpkg --get-selections` before mutation.
- Pre-mutation upgradable list.
- Package scope approved by operator.
- Apt logs from the mutation window.
- Post-mutation package versions if the upgrade partially succeeds.

The exact package rollback command must be derived from those artifacts at
incident time and reviewed before execution. This Phase 28 runbook intentionally
does not include a generic downgrade command because package rollback is
version-specific and host-specific.

### Ubuntu Pro and ESM Rollback Notes

Keep only redacted Pro status in shared artifacts. Token values, account IDs,
contract IDs, and email values must not be copied into docs or logs.

If attach/service repair is required in Phase 29, use the approved secret path
on the host or an operator-provided secret at execution time. Never paste the
token into planning files.

### Landscape Notes

Landscape is SaaS-first for G18. Phase 28 records only client presence and
registration observations. Re-registration, SaaS UI confirmation, or deployment
changes are Phase 29-only and require explicit approval.

### RDP/XRDP Notes

The canonical fleet map says human XRDP uses display `:1..14`; SRV-1, SRV-2,
and SRV-3 use `:1` as primary, with VNC `5901` and RDP client-controlled
resolution. Phase 29 RDP validation should preserve that posture.

Do not restart XRDP/RDP in Phase 28. If Phase 29 must restart or repair XRDP,
the approval record must name the config backup path and rollback target.
