# Phase 14 Plan 06: Jenkins Agent on K3s (M005 extension)

## Performance

- **Estimated duration:** 2-4 hours
- **Status:** ready (M005 live, 14-05 complete)
- **Depends on:** 14-05 (Jenkins docker-deps cleanup), M005 live K3s HA

## Goal

Estender o M005 (K3s HA + Portainer live) com um Jenkins agent rodando
como Deployment no cluster K3s. O agent recebe jobs via JNLP do Jenkins
controller (que continua em SRV-1, gerenciado por Podman systemd-user) e
executa builds em pods efêmeros usando Podman/buildah em vez de Docker.

## Motivation

Hoje o Jenkins controller (srv1, rodando em Podman desde 14-05) só tem
ele mesmo como executor. Builds de pipeline que precisariam de workers
isolados ou paralelismo dependem de Docker socket — que não existe
mais. Com o cluster K3s HA já live (M005), o caminho natural é:

1. Instalar o **Kubernetes plugin** no Jenkins controller
2. Criar uma **conta de serviço K8s** + **secret** no cluster pra JNLP
3. Deployar um **Jenkins agent** como Deployment no cluster
4. Configurar **Pod templates** por tipo de job (maven, node, python)
5. Validar com um job de smoke (`hello world` + `podman build` simples)

Isso substitui o modelo "DinD no Jenkins" (que nunca funcionou bem) por
"agent in K3s, build ephemeral pod". Builds que precisavam de Docker
socket agora rodam em pods limpos que aparecem e somem por job.

## Tasks

### Task 1: Instalar o Kubernetes plugin no controller

```bash
# Plugin id: kubernetes
# Acessar https://jenkins.atius.com.br/ → Manage Jenkins → Plugins → Available
# Buscar "Kubernetes", marcar, Install without restart
# Reiniciar o controller se necessário
systemctl --user restart container-jenkins.service
```

### Task 2: Service account + secret no cluster K3s

```bash
# No SRV-1 (ou qualquer control-plane)
kubectl create namespace jenkins
kubectl -n jenkins create serviceaccount jenkins-agent
kubectl -n jenkins create secret generic jenkins-agent \
  --from-literal=jenkins-jnlp-url=http://10.1.1.1:8085 \
  --from-literal=jenkins-secret=$(openssl rand -hex 32)
```

### Task 3: Deployment do Jenkins agent

Imagem: `localhost/jenkins:podman-latest` (mesma do controller) — assim
o agent herda o toolchain e não precisa de imagem dedicada. JNLP
port 50000 conecta ao controller via `10.1.1.1:50000` (já exposto no
compose).

```yaml
# modules/k3s-ha-portainer-oci/jenkins/agent-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: jenkins-agent
  namespace: jenkins
  labels:
    app: jenkins-agent
    managed-by: omni-srv-admin
spec:
  replicas: 2
  selector:
    matchLabels:
      app: jenkins-agent
  template:
    metadata:
      labels:
        app: jenkins-agent
    spec:
      serviceAccountName: jenkins-agent
      containers:
        - name: jnlp
          image: localhost/jenkins:podman-latest
          command: ["/bin/sh", "-c"]
          args:
            - |
              set -e
              apt-get update && apt-get install -y --no-install-recommends openssl ca-certificates
              curl -sO http://10.1.1.1:8085/jnlpJars/agent.jar
              echo "${JENKINS_SECRET}" > /tmp/secret
              exec java -jar agent.jar -jnlpUrl http://10.1.1.1:8085/computer/${JENKINS_AGENT_NAME}/slave-agent.jnlp -secret @/tmp/secret -workDir /home/jenkins/agent
          env:
            - name: JENKINS_AGENT_NAME
              value: k3s-agent-$(HOSTNAME)
            - name: JENKINS_SECRET
              valueFrom:
                secretKeyRef:
                  name: jenkins-agent
                  key: jenkins-secret
          resources:
            requests:
              cpu: "500m"
              memory: "1Gi"
            limits:
              cpu: "2"
              memory: "4Gi"
```

```bash
kubectl -n jenkins apply -f modules/k3s-ha-portainer-oci/jenkins/agent-deployment.yaml
kubectl -n jenkins get pods -l app=jenkins-agent -w
```

### Task 4: Configurar Pod templates no Jenkins controller

Via UI Jenkins (Manage Jenkins → Clouds → Kubernetes → Add Pod Template):
- Name: `k3s-podman`
- Namespace: `jenkins`
- Label: `k3s`
- Container template: `localhost/jenkins:podman-latest`, command `sleep 99999`
- Mounts: `/var/jenkins_home` (workspace), `docker-config` (registry auth)

### Task 5: Smoke test

Criar um job de pipeline com `agent { label 'k3s' }` e steps:
```groovy
podTemplate(label: 'k3s-test', containers: [
  containerTemplate(name: 'podman', image: 'localhost/jenkins:podman-latest', command: 'sleep', args: '99999')
]) {
  node('k3s-test') {
    stage('build') {
      container('podman') {
        sh 'podman --version && podman run --rm hello-world'
      }
    }
  }
}
```

Esperar: pod `k3s-test-*` aparece no cluster, executa, some. Log mostra
`podman --version` + `hello-world` rodando.

## Success Criteria

- [ ] Jenkins controller tem o Kubernetes plugin instalado
- [ ] Cluster K3s tem namespace `jenkins` com SA + secret
- [ ] 2 Jenkins agent pods rodando no cluster e registrados no controller
- [ ] Job de pipeline smoke (`hello-world` via podman) roda fim-a-fim
- [ ] Build pod é criado, roda, e some — sem leak de pods órfãos
- [ ] Nenhum agent depende de `/var/run/docker.sock` ou `/usr/bin/docker`

## Risks

- **Imagem do agent herda apt-get do Debian (não Ubuntu):** confirmado
  via Dockerfile da imagem `localhost/jenkins:podman-latest`. Em jobs que
  precisem de toolchain específica, usar `containerTemplate` por job.

- **JNLP vai pela wg0 (10.1.1.1) e não pela VPN pública:** aceito.
  Cluster não é exposto publicamente; controller fala direto via wg0.

- **Resource governor (M006) sobre agentes K3s:** os pods do agent vão
  herdar os limits do namespace `jenkins`. Aplicar ResourceQuota:
  ```yaml
  apiVersion: v1
  kind: ResourceQuota
  metadata:
    name: jenkins-quota
    namespace: jenkins
  spec:
    hard:
      requests.cpu: "4"
      requests.memory: "8Gi"
      limits.cpu: "8"
      limits.memory: "16Gi"
  ```
