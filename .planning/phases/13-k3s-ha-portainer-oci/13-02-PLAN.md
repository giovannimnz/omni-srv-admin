# 13-02: PTP fallback mesh for K3s nodes

## Objective

Desenhar uma malha PTP de fallback entre `ATIUS-SRV-1`, `ATIUS-SRV-2` e
`ATIUS-SRV-3`, alem do WireGuard `wg0`, para reduzir risco de perda de
comunicacao entre control-plane/etcd.

## Critical Constraint

K3s v1 anuncia os nodes como `10.1.1.1`, `10.1.1.2` e `10.1.1.7` em `wg0`.
Um fallback transparente para K3s precisa manter esses IPs alcançaveis quando
`wg0` falhar. Se o fallback usar outro CIDR apenas, ele serve como caminho de
administracao/DR, mas nao como failover transparente de API/etcd/kubelet.

Nao mudar `node-ip`, `advertise-address`, token, peers etcd ou rotas live sem
snapshot/backup, janela de manutencao e rollback.

## Topology Target

Full mesh PTP:

| Link | Purpose |
|---|---|
| SRV-1 <-> SRV-2 | Fallback for quorum/control-plane reachability |
| SRV-1 <-> SRV-3 | Fallback for quorum/control-plane reachability |
| SRV-2 <-> SRV-3 | Fallback for east-west traffic and quorum resilience |

## Candidate Designs

| Option | Description | Pros | Risk |
|---|---|---|---|
| Admin/DR PTP | Separate fallback CIDR used only for SSH, diagnostics and recovery | Simple, low risk | Does not keep K3s alive if `wg0` fails |
| Transparent route fallback | Health-checked routes preserve reachability to `10.1.1.x` through PTP links | Can protect K3s without changing node identity | Needs careful routing to avoid asymmetric traffic/split-brain |
| OCI VCN fallback | Cross-account VCN peering or equivalent private underlay | Can be private if every account is configured correctly | Separate OC1 accounts make this a larger network project, not an M005 assumption |

Preferred path for M005: design and validate Admin/DR PTP first; promote to
transparent route fallback only after a lab/maintenance-window test proves
route convergence and rollback.

## Task 0 — No live mutation

This plan is design-first. Do not create tunnels, change host routes, change
firewall rules or restart WireGuard/K3s during planning.

## Task 1 — Map current underlay and ports

Use the vault baseline before defining any new port:

- `60-LOGS/2026-06-13-m004-network-port-baseline.md`
- `60-LOGS/2026-06-13-m005-execute-phase-checkpoint.md`

Per node, collect read-only data:

```bash
ip -br addr
ip route
ip rule
sudo ss -H -lntup
sudo ss -H -lnuap
```

Record:

- public IP
- OCI VCN IP
- OCI account/tenancy label or operator-owned alias, without secrets
- WireGuard IP
- current UDP/TCP listeners
- current firewall implementation (`iptables`, `nftables`, `ufw`, OCI rules)
- whether any cross-account OCI private path exists; default assumption is no
  shared VCN/NSG between SRV-1/SRV-2/SRV-3

## Task 2 — Choose PTP transport and addressing

Produce a table with:

- transport
- interface names
- CIDRs
- listening ports
- source/destination restrictions
- per-account OCI ingress/egress rules
- owner service/systemd unit
- rollback command

Rules:

- Do not reuse Kubernetes service/pod CIDRs.
- Do not expose K3s ports publicly.
- Do not put secrets in git, logs or vault.
- Prefer deterministic interface names and explicit route metrics.

## Task 3 — Define failover model

Choose one:

1. Admin/DR fallback only.
2. Transparent route fallback for `10.1.1.x`.

If choosing transparent route fallback, document:

- health check interval and failure threshold
- route metric changes
- route rollback
- how asymmetric routes are prevented
- how split-brain is prevented if only one link fails
- how etcd quorum is validated after failover

## Task 4 — Validation scenarios

Dry-run scenarios to document before live testing:

| Scenario | Expected Result |
|---|---|
| All links healthy | K3s uses `wg0`; PTP standby does not steal traffic |
| SRV-1 <-> SRV-2 wg path fails | Admin/DR path remains available; transparent mode preserves `10.1.1.x` if enabled |
| One PTP link fails | Remaining links do not create asymmetric routing loops |
| SRV-1 isolated | etcd quorum behavior understood; no unsafe writes if quorum lost |
| Rollback | Routes/firewall/interfaces return to pre-change state |

## Task 5 — Production-ready gate

Before declaring M005 production-ready:

- PTP design is committed in repo and documented in the vault.
- Snapshot/backup exists for all nodes.
- Port/IP baseline pre-change and post-change are recorded.
- At least one failover test is executed in a maintenance window.
- Rollback has been tested or dry-run with commands reviewed.

## Acceptance

- The cluster can still bootstrap using only `wg0`.
- PTP fallback is clearly classified as Admin/DR or transparent K3s failover.
- No K3s advertised address changes are required during normal operation.
- No public K3s ports are opened.
- No new secrets are committed.
